# ai-provenance-fixtures

Content-provenance test fixtures: three versioned transformation
chains — a PNG image and two text assets — that start with provenance
assertions bound to their content and are then re-encoded, stripped,
resized, excerpted and copied, step by documented step. Every step
records what can still be verified, what has become unknown, and what
is lost, and a small checker proves the fixtures actually behave that
way.

## The problem

Content rarely stays in the file it was created in. An image gets
re-encoded by a platform, resized for a thumbnail, stripped of its
metadata by a privacy tool. A disclosure statement gets copied as body
text and leaves its header behind. At each hop, the claims that were
attached to the content — who made it, when, under what licence, with
what disclosure — may survive, may survive in a form that no longer
matches the content, or may vanish silently.

Tools that check provenance (including our own
[ProvenanceGuard](https://provenanceguard.getingeniousai.com) and
[DisclosureGuard](https://disclosureguard.getingeniousai.com)) need
test data where the correct answer at every hop is known in advance:
not "the metadata looks fine", but "after this exact resize, these
assertions must read *unknown*, because they are bound to pixels that
no longer exist". That is what this repo is: ground truth for
provenance verification, built as fixtures with expected verdicts,
plus a reference checker that computes the verdicts from the files
themselves rather than trusting the manifest.

## Verdict honesty — read this first

- **A hash match proves the bytes match the record. Nothing else.**
  It does not prove the content is authentic, that the assertions in
  it are true, or that the named creator made it. Anyone can write a
  header claiming anything; these fixtures make a claim's *carriage*
  (is it still with the asset?) and *binding* (was it made about
  exactly this content?) testable. Truth is out of scope, deliberately.
- **"Verified" is a statement about a record, not about the world.**
  It means: this assertion is still carried with the asset, and the
  payload hash it was bound to equals the payload hash of the content
  in front of you.
- **"Unknown" is the most common honest answer in real pipelines.**
  The claim is present, the content has moved on, and no one can tell
  from the asset alone whether the claim still describes it. A checker
  that reports "verified" here is lying to you.
- **"Lost" is silent in the wild.** Nothing in a stripped file says
  anything is missing. These fixtures record the loss because the
  chain was documented as it happened; a file found on its own gives
  you no such record. The fixtures exist so tools can be tested on
  the distinction.
- All content here is synthetic, generated by a script in this repo
  (`tools/build_fixtures.py`) from recipes in code. No real person,
  place, event or third-party work is depicted or included.

## The three chains (v1)

Every chain carries the same five assertions — `creator`,
`created_at`, `license`, `ai_disclosure`, `content_description` —
bound at creation to the payload hash of the original content.

### harbour-light — PNG image, 5 steps

| Step | Transformation | Expected |
|---|---|---|
| 0 `original` | Created; assertions embedded as PNG `tEXt` chunks | verified |
| 1 `re-encode` | Same pixels, Sub row filter — file bytes change, pixels don't | verified |
| 2 `strip-metadata-sidecar` | `tEXt` chunks stripped; assertions move to a sidecar file | verified (sidecar) |
| 3 `resize-sidecar-stale` | Resized 48×32 → 24×16; sidecar kept, bound to the old pixels | **unknown** |
| 4 `crop-no-carriage` | Cropped to 16×12; no embedded metadata, no sidecar | **lost** |

### field-notes — text, 4 steps

| Step | Transformation | Expected |
|---|---|---|
| 0 `original` | Provenance header block bound to the normalised body hash | verified |
| 1 `rewrap` | Paragraphs re-wrapped 88 → 64 columns (same words) | verified |
| 2 `excerpt` | First paragraph only; original header copied across | **unknown** |
| 3 `strip-header` | Header removed; the excerpt circulates bare | **lost** |

### disclosure-card — text, 3 steps

| Step | Transformation | Expected |
|---|---|---|
| 0 `original` | Disclosure + assertions in the header | verified |
| 1 `crlf-re-encode` | Whole file re-encoded with CRLF line endings | verified |
| 2 `body-only-copy` | Body copied without its header — the commonest real-world hop | **lost** |

Totals: 12 steps, 60 assertion-status expectations, each step
hash-chained to the previous step's record.

## How verification works

For every step the checker recomputes, from the files on disk:

1. the asset's SHA-256, against the recorded asset hash;
2. the payload hash from the decoded content (PNG pixels with filters
   removed; text body whitespace-normalised), against the record;
3. the step's record hash and its link to the previous step's record
   (the hash chain — editing any recorded fact breaks it);
4. each assertion's actual status — found embedded or in the sidecar,
   binding compared with this step's payload hash — against the
   expected status in the manifest.

The full format is documented in [docs/FORMAT.md](docs/FORMAT.md).

## Install and use

Python ≥ 3.9, standard library only, no network access.

```bash
git clone https://github.com/Iceman2050/ai-provenance-fixtures
cd ai-provenance-fixtures

python -m provenance_fixtures                  # verify all chains
python -m provenance_fixtures --list           # list chains
python -m provenance_fixtures --chain harbour-light
python -m unittest discover -s tests -v        # the full test suite
python tools/build_fixtures.py                 # regenerate fixtures (byte-identical)
```

Exit codes: `0` = every hash, chain link and expected status verified;
`1` = at least one check failed; `2` = usage / IO error.

## Exact supported scope

- **Formats:** 8-bit RGBA PNG (colour type 6, non-interlaced) with
  `tEXt` carriage; UTF-8 text with the header-block carriage defined
  in `docs/FORMAT.md`; JSON sidecars. The PNG codec is a minimal
  teaching implementation, not a general PNG library.
- **Assertions:** the five fixture assertions, bound as one set to one
  payload hash per chain. Per-assertion bindings, signatures, and
  multi-party assertion sets are out of scope for v1.
- **Not in scope:** C2PA manifests, cryptographic signing, XMP/EXIF/
  IPTC carriage, JPEG/WebP/audio/video fixtures, perceptual hashing.
  Those are real provenance mechanisms; this repo's job is the
  ground-truth fixture layer underneath whichever mechanism a tool
  implements, and it says so rather than imitating them.

## Limitations

- The bindings are hashes, not signatures. Nothing stops someone from
  writing a fresh header over someone else's content and binding it
  correctly — the result would verify. Provenance systems that need
  attribution to hold up need signing keys and identity on top of a
  layer like this one; the fixtures model the carriage/binding half
  of the problem only.
- The text payload hash is whitespace-insensitive by design, so it
  cannot detect reordering of whitespace — and more importantly it
  binds *words in order*, not meaning. A paraphrase keeps no binding;
  a word-for-word copy keeps it entirely. Both behaviours are
  documented, and both are the honest limits of a text hash.
- The PNG payload hash is pixel-exact: a one-pixel change breaks it.
  Near-duplicate detection needs perceptual hashing, which v1
  deliberately does not fake.
- The chains are short (3–5 steps) and synthetic. Real pipelines are
  longer and messier; the fixtures are a test floor, not a survey of
  everything platforms do to content.

## Relationship to ProvenanceGuard and DisclosureGuard

[ProvenanceGuard](https://provenanceguard.getingeniousai.com) tracks
asset transformation lineage — chains of hashes, source references
and transformations, with explicit visibility into what can and
cannot be verified after metadata is stripped; these fixtures are its
open, standalone ground truth.
[DisclosureGuard](https://disclosureguard.getingeniousai.com) checks
whether disclosure signals survive editing and publishing to the
actual output file; the `disclosure-card` chain is that exact test in
miniature — including the step where the disclosure does not survive,
because a fixture set that only contains passes teaches a checker to
say "fine" to everything.
